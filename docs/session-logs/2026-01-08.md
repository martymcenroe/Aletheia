Session Log: Security Pipeline Upgrade & The "Warrior" Shift
Date: January 8-9, 2026 Topic: Security Hardening, Automated Governance, & Audit Fidelity Trigger: Firefox Store rejection due to innerHTML usage (XSS vulnerability).

1. Executive Summary
This session marked a fundamental pivot in Aletheia's engineering culture from "Passive Compliance" (checking boxes) to "Active Governance" (enforcing constraints).

We diagnosed the root cause of the XSS failure as "Tunnel Vision" (focusing on AI Safety while ignoring App Security). We remediated this by deploying a robust local security pipeline, hardening the codebase against advanced threats (DOM Clobbering, Message Spoofing), and fixing a critical "Lazy Auditor" process failure where tools were reporting successes without actually running.

Finally, we corrected a logic drift in the Guardrails system where high-register vocabulary ("immiserate") was being flagged as "Archaic," enforcing a strict distinction between Hard Blocks (Safety) and Soft Blocks (Education).

2. The Vulnerability Gap Analysis (Post-Mortem)
Findings
The Failure: We relied on "Security by Store Review." Our internal audits passed because eslint was only checking for syntax/logic, not security.

The Blind Spot: Previous audits (0809) focused exclusively on LLM Output Safety (preventing prompt injection) and ignored UI Scaffolding Security (preventing XSS in overlay.js).

Identified Risks:

DOM Clobbering: Host pages hijacking id="aletheia-overlay-host".

Message Spoofing: Malicious extensions sending fake messages to service-worker.js.

Supply Chain: npm dev dependencies running unchecked.

The Fix (PR #196)
We implemented a "Defense in Depth" strategy:

Tooling:

Installed eslint-plugin-no-unsanitized (The specific fix for innerHTML).

Installed eslint-plugin-security.

Enabled flake8-bandit ("S" select) in ruff for Python backend security.

Added web-ext lint to CI to simulate Firefox Store reviews.

Code Hardening:

Anti-Spoofing: Added if (sender.id !== chrome.runtime.id) return; to service-worker.js.

Anti-Clobbering: Removed reliance on document.getElementById for overlay management; switched to a stored variable reference (overlayHostRef).

Documentation:

Split docs/0809 into 0809-audit-app-security.md (Engineering) and 0825-audit-ai-safety.md (Risk) to prevent future tunnel vision.

3. The "Warrior Audit" Intervention
The Incident

The Correction
We established the "Positive Confirmation" protocol (docs/0813 §6.1):

Rule: A silent tool is a broken tool. "0 errors" is only a pass if accompanied by "X files scanned."

Action:

Added npm run lint scripts to package.json.

4. Shadow DOM Hardening (Issue #197)
The Problem
Audit revealed attachShadow({ mode: 'open' }) was used in 6 locations, violating ADR 0202. This allowed host pages to access and manipulate the Aletheia overlay.

The Solution: "The Reference Pattern"
Changing to mode: 'closed' breaks the host.shadowRoot property. We designed a specific pattern to maintain functionality:

State: Use a module-level variable let activeShadowRoot = null;.

Capture: Assign activeShadowRoot = host.attachShadow({ mode: 'closed' }) at creation.

Cleanup: Explicitly set activeShadowRoot = null in removeOverlay().

Legacy: Updated window.updateAletheiaOverlay to use the variable instead of the DOM property.

Verification: Gemini reviewed the implementation and the test suite (tests/e2e/shadow-dom-security.spec.js) to ensure Claude didn't "cheat" the test by running it in a privileged context.

5. Governance as Code (Horizon Scanning)
We analyzed the ChrisWiles/claude-code-showcase repo and adopted two "Shift Left" strategies:

PostToolUse Hooks: Configured .claude/settings.json to run eslint immediately after the AI writes a .js file. This forces the Agent to self-correct security violations instantly.

Role-Based Agents: Created .claude/agents/security-reviewer.md with a strict checklist (No innerHTML, Validate sender.id) to act as the "Bad Cop" in reviews.

6. Guardrails Logic Drift (Issue #XXX)
The Issue
The system was flagging formal vocabulary (e.g., "immiserate" in WSJ) as "Archaic" and applying a Hard Block (403 Forbidden), preventing usage.

The Fix (Architecture)
We redefined the logic in docs/1126-hard-soft-blocking.md:

Hard Block (Stop): Hate Speech, Harassment, Dangerous Content.

Soft Block (Warn): Archaic, Provocative, Bias. (User sees warning, has "Analyze Anyway" button).

Definition Update:

Archaic: Words dead before 1950 (e.g., "Forsooth").

Formal/Academic: High-register words currently in use (e.g., "Immiserate"). Do Not Block.
