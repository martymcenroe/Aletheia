### 2.5 Logic Flow (Pseudocode)

```
=== Phase 1: Health Check Route ===

1. Receive HTTP request
2. IF path == "/health" AND method == "GET":
   a. Return {"status": "ok", "version": "1.0"} with 200
   b. Skip auth, skip origin secret check
3. ELSE: continue to existing handler

=== Phase 2: Extension Error Handling ===

1. Create AbortController with 30s timeout
2. Fetch API with signal from controller
3. Record start time
4. ON response:
   a. Calculate latency
   b. IF status >= 400:
      - Map status to user-friendly message
      - IF 429: parse resets_in_seconds from body
   c. Validate response has signal/gem fields
   d. Store diagnostics in chrome.storage.session
   e. IF CSP blocks overlay injection:
      - Fall back to chrome.notifications
5. ON timeout (AbortError):
   a. Store timeout diagnostic
   b. Show "Request timed out" message

=== Phase 3: Overlay Error Rendering ===

1. Receive (response, httpStatus)
2. IF httpStatus == 401:
   a. Show config error message (not hard block)
3. IF httpStatus == 429:
   a. Show rate limit with countdown timer
4. IF response missing signal/gem:
   a. Show "Unexpected Response" message
5. ELSE: render normal overlay

=== Phase 4: Popup Diagnostics ===

1. On popup open: read chrome.storage.session
2. Display version footer: "v1.0"
3. Display last request: status, latency, timestamp
4. Display last error if present

=== Phase 5: CloudWatch Alerting ===

1. Create alarm: Aletheia-LambdaErrors (Errors > 0 in 5 min)
2. Create alarm: Aletheia-4xxRate (4xx > 50% in 15 min)
3. Create alarm: Aletheia-5xxRate (5xx > 10% in 15 min)
4. Create alarm: Aletheia-LambdaThrottles (Throttles > 0 in 5 min)
5. All alarms → SNS topic Aletheia-CapDenialAlerts

=== Phase 6: Metrics Endpoint ===

1. Receive HTTP request
2. IF path == "/metrics" AND method == "GET":
   a. Validate admin JWT
   b. Query DynamoDB for user/tier/usage data
   c. Return metrics JSON matching admin dashboard schema
```

### 2.6 Technical Approach

* **Module:** `src/lambda_function.py` (routing), extension JS files (error handling), `docs/runbooks/provision-cloudwatch.sh` (alarms)
* **Pattern:** Path-based routing in Lambda, defensive error handling in extension, infrastructure-as-code for alarms
* **Key Decisions:**
  - Health check placed before auth gate for zero-auth monitoring
  - 30s timeout matches Lambda's 60s timeout with margin
  - `chrome.storage.session` for diagnostics (cleared on browser restart, no persistence overhead)
  - `chrome.notifications` as CSP fallback when overlay injection fails
  - Alarm thresholds conservative for low-traffic MVP

### 2.7 Architecture Decisions

| Decision | Options Considered | Choice | Rationale |
|----------|-------------------|--------|-----------|
| Health check auth | No auth, origin-secret only, full auth | No auth | Health probes must work from any source (UptimeRobot, curl) |
| Fetch timeout | No timeout, 15s, 30s, 60s | 30s | Matches Lambda timeout with margin; prevents infinite waits |
| Diagnostics storage | localStorage, chrome.storage.local, chrome.storage.session | chrome.storage.session | Cleared on restart, no persistence cost, service worker accessible |
| CSP fallback | Silent fail, console log, chrome.notifications | chrome.notifications | User gets feedback even when CSP blocks content scripts |
| Alarm notification | New SNS topic, existing topic | Existing `Aletheia-CapDenialAlerts` | Reuse existing infrastructure, single notification channel |
| Error message style | Technical details, user-friendly, hybrid | User-friendly | Users are not developers; hide implementation details |

## 3. Requirements

1. `GET /health` returns `{"status":"ok","version":"1.0"}` with HTTP 200
2. Health check requires no auth and no origin secret
3. `POST /health` falls through to normal handler (health is GET-only)
4. Extension fetch has 30s AbortController timeout
5. HTTP 401 shows "Service configuration error. This has been logged."
6. HTTP 429 shows "Limit reached. Resets in {N} minutes." with parsed reset time
7. HTTP 500 shows "Server error. Try again shortly."
8. Fetch timeout shows "Request timed out. Try again."
9. Response without `signal`/`gem` shows "Unexpected Response" instead of blank
10. Diagnostics (status, latency, timestamp, error) stored in `chrome.storage.session`
11. 401 in overlay not rendered as hard block (distinct from 403)
12. Popup displays version footer `v1.0`
13. Popup displays diagnostics panel (last request status, latency, timestamp)
14. CloudWatch alarm `Aletheia-LambdaErrors`: Errors > 0 in 5 min
15. CloudWatch alarm `Aletheia-4xxRate`: 4xx > 50% in 15 min
16. CloudWatch alarm `Aletheia-5xxRate`: 5xx > 10% in 15 min
17. CloudWatch alarm `Aletheia-LambdaThrottles`: Throttles > 0 in 5 min
18. All alarms notify via existing SNS topic `Aletheia-CapDenialAlerts`
19. `GET /metrics` returns user/tier/usage data matching admin dashboard schema
20. `/metrics` endpoint requires admin JWT
21. `chrome.notifications` used as fallback when CSP blocks overlay injection

## 4. Alternatives Considered

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| Separate health Lambda | Complete isolation | Extra infra, cost, maintenance | **Rejected** |
| Health check as Lambda URL path | Simple routing | Shares auth gate complexity | **Selected** (routed before auth) |
| Extension telemetry to backend | Centralized error tracking | Privacy concern, extra API calls | **Rejected** for MVP |
| chrome.storage.local for diagnostics | Persists across restarts | Unnecessary persistence, cleanup needed | **Rejected** |
| Separate SNS topics per alarm | Granular notifications | Notification fatigue, extra infra | **Rejected** |

## 7. Security & Safety Considerations

### 7.1 Security

| Concern | Mitigation | Status |
|---------|------------|--------|
| Health check information leak | Returns only `{"status":"ok","version":"1.0"}` — no internal state | Addressed |
| Metrics endpoint unauthorized access | Requires admin JWT via `@require_auth` | Addressed |
| XSS in error messages | All error messages are static strings, not user input | Addressed |
| Notification spoofing | `chrome.notifications` only triggered by service worker, not content scripts | Addressed |
| Diagnostics data exposure | `chrome.storage.session` cleared on restart, no PII stored | Addressed |

### 7.2 Safety

| Concern | Mitigation | Status |
|---------|------------|--------|
| Health check used for DoS | Lightweight handler, no DB calls, CloudFlare rate limiting still active | Addressed |
| Alarm notification storm | Alarm periods (5-15 min) prevent rapid re-firing | Addressed |
| Timeout too aggressive | 30s is generous; Lambda timeout is 60s | Addressed |
| CSP fallback notification spam | Notifications only shown once per analysis attempt | Addressed |

**Fail Mode:** Fail Open — Extension errors show user-friendly messages. Lambda health check is stateless. Alarm failures don't affect API.
